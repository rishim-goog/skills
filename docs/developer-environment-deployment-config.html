Configure CI/CD and Deployment Defaults (deployment-config.json)

Target Documentation Page: https://docs.cloud.google.com/docs/get-started/developer-environment
Placement: Immediately following the “Install the google-cloud-developer plugin” section (with administrator setup bullets added to “Before you begin”).

1. Addition to “Before you begin” (Administrator Prerequisites)

Add the following items to the Before you begin section of Set up a local development environment:

  • Publish an organization deployment configuration (deployment-config.json): (Optional, recommended for teams) Create and host a shared deployment-config.json file in a central Git repository (GitHub, GitLab, or Bitbucket) to define standard runtime targets (Cloud Run or GKE), Artifact Registry repositories, Developer Connect connections, and Binary Authorization policies across dev and prod environments.
  • Provision a dedicated Cloud Build service account: Create a least-privilege, user-managed service account (for example, cloudbuild-runner@YOUR_PROJECT_ID.iam.gserviceaccount.com) rather than using the default Compute Engine service account for CI/CD triggers.

2. Configure CI/CD and deployment defaults (deployment-config.json)

After you install the google-cloud-developer plugin in Antigravity, Claude Code CLI, or Codex CLI, the Google Cloud CI/CD skills (google-cicd-deploy, google-cicd-pipeline-design, and google-cicd-release-orchestration) use a standardized deployment-config.json configuration file to automate container builds, supply-chain security checks, and deployments to Cloud Run and Google Kubernetes Engine (GKE).

Providing a deployment-config.json file eliminates repetitive prompts for project IDs, regions, Artifact Registry paths, GKE cluster names, and Cloud Build settings, while enforcing your organization’s security guardrails across dev and prod environments.

How agents resolve deployment configuration

When you ask your agent to build or deploy an application, AI agent, or Model Context Protocol (MCP) server, the CI/CD skills resolve configuration in the following order:

Priority 1

Cached Workspace Configuration

If .gcp-deploy/deployment-config.json (or ./deployment-config.json) already exists in your project workspace, the agent uses it immediately without prompting you or running unnecessary network fetches.

Priority 2

Agent Workspace Context Files

If no deployment-config.json file is present, the agent checks your agent-specific workspace instructions file (GEMINI.md for Antigravity/Gemini CLI, CLAUDE.md for Claude Code CLI, or AGENTS.md for Codex CLI) or your prompt.

Priority 3

Central Git Repo or Auto-Generation

For new projects without local configuration, instruct the agent to either pull deployment-config.json from a central Git repository (GitHub, GitLab, or Bitbucket) or auto-generate deployment-config.json from your Google Cloud project.

Set up deployment-config.json

Choose one of the following methods to configure deployment-config.json in your local development environment:

Option 1: Pull deployment-config.json from a central Git repository (Recommended for teams)

Platform administrators can maintain a single deployment-config.json in a shared Git repository on GitHub, GitLab, Bitbucket, or any Git server.

  1. In your agent (Antigravity, Claude Code CLI, or Codex CLI), prompt the agent with your configuration repository URL: 
    Deploy my application to the dev environment using the deployment configuration in https://github.com/YOUR_ORG/YOUR_CONFIG_REPO
  2. The agent automatically:
    • Fetches deployment-config.json using Git sparse-checkout (git clone --depth 1 --filter=blob:none --sparse).
    • If the configuration repository is private and local Git credentials are not configured, retrieves a short-lived read token via Google Cloud Developer Connect (gcloud developer-connect connections git-repository-links fetch-read-token) across GitHub, GitLab, or Bitbucket.
    • Caches the file at .gcp-deploy/deployment-config.json, records the source URL in .gcp-deploy/config-state.json, and adds .gcp-deploy/ to .gitignore and .dockerignore.

Option 2: Auto-generate deployment-config.json from your Google Cloud project

If your organization does not maintain a central configuration repository, your agent can generate a compliant deployment-config.json file by inspecting the APIs and resources enabled in your Google Cloud project:

  1. Ensure your default project is set in the gcloud CLI: 
    gcloud config set project YOUR_PROJECT_ID
  2. Prompt your agent: 
    Generate a deployment configuration file based on the services enabled in my GCP environment.
    (Or specify a subset of services, for example: "Generate a deployment configuration file that utilizes Cloud Run, Artifact Registry, Developer Connect, and Cloud Build.")
  3. The agent inspects your enabled APIs (gcloud services list --enabled), existing Artifact Registry repositories, Developer Connect connections, Cloud Run services, and GKE clusters, and writes the resulting configuration to ./deployment-config.json and .gcp-deploy/deployment-config.json.

deployment-config.json schema and example 

{
  "active_runtime": "Cloud Run",
  "default_environment": "dev",
  "fail_on_push_error": true,
  "common_gcp_settings": {
    "project_id": "YOUR_PROJECT_ID",
    "region": "us-central1"
  },
  "cloud_run": {
    "dev": {
      "project_id": "YOUR_PROJECT_ID",
      "region": "us-central1",
      "artifact_registry": "us-central1-docker.pkg.dev/YOUR_PROJECT_ID/app-images-dev",
      "service_name": "<app-name>-dev",
      "public_access": true,
      "container_port": 8080
    },
    "prod": {
      "project_id": "YOUR_PROJECT_ID",
      "region": "us-central1",
      "artifact_registry": "us-central1-docker.pkg.dev/YOUR_PROJECT_ID/app-images-prod",
      "service_name": "<app-name>-prod",
      "public_access": false,
      "container_port": 8080,
      "require_confirmation": true,
      "binary_authorization": "default",
      "binary_authorization_policy": "prod-policy"
    }
  },
  "gke": {
    "dev": {
      "project_id": "YOUR_PROJECT_ID",
      "cluster_location": "us-central1",
      "cluster_name": "gke-cluster-dev",
      "namespace": "dev",
      "artifact_registry": "us-central1-docker.pkg.dev/YOUR_PROJECT_ID/app-images-dev",
      "manifest_path": "./kubernetes-manifests/"
    },
    "prod": {
      "project_id": "YOUR_PROJECT_ID",
      "cluster_location": "us-central1",
      "cluster_name": "gke-cluster-prod",
      "namespace": "prod",
      "artifact_registry": "us-central1-docker.pkg.dev/YOUR_PROJECT_ID/app-images-prod",
      "manifest_path": "./release/kubernetes-manifests.yaml",
      "require_confirmation": true
    }
  },
  "developer_connect_and_cloud_build": {
    "build_mode": "Developer Connect + Cloud Build",
    "developer_connect": {
      "location": "us-central1",
      "connection_id": "YOUR_DEVCONNECT_CONNECTION_ID"

      "project_id": "YOUR_PROJECT_ID",

    }
  }
}

Configuration field reference

1. Top-level and common settings

FieldTypeRequiredDescription
active_runtimestringYesDefault target runtime when not specified in the user prompt. Allowed values: "Cloud Run", "GKE", or "prompt" (asks the developer to choose).
default_environmentstringYesDefault target environment when not specified in the user prompt ("dev" or "prod").
fail_on_push_errorbooleanYesWhen true (recommended), immediately aborts the deployment if pushing the container image to Artifact Registry fails, preventing fallback to external or public registries.
common_gcp_settings.project_idstringYesDefault Google Cloud project ID.
common_gcp_settings.regionstringYesDefault Google Cloud region (for example, "us-central1").

2. Cloud Run settings (cloud_run.dev and cloud_run.prod)

FieldTypeRequiredDescription
project_id / regionstringYesTarget Google Cloud project ID and deployment region for the Cloud Run service.
artifact_registrystringYesFull Artifact Registry Docker repository URI (<REGION>-docker.pkg.dev/<PROJECT_ID>/<REPO_NAME>).
service_namestringYesNaming template for the Cloud Run service. Supports <app-name> substitution derived from the Git repository or directory name (for example, "<app-name>-dev").
public_accessbooleanYesWhen true, passes --allow-unauthenticated; when false, enforces IAM authentication (--no-allow-unauthenticated).
container_portintegerYesPort on which the container listens (default: 8080).
require_confirmationbooleanOptionalWhen true (enforced on prod), requires explicit user confirmation before executing the deployment.
binary_authorizationstringOptionalBinary Authorization policy name to enforce on the Cloud Run service (for example, "default" on prod passes --binary-authorization=default).
binary_authorization_policystringOptionalIdentifier for the Binary Authorization policy used to verify image attestations prior to prod deployment.

3. Google Kubernetes Engine settings (gke.dev and gke.prod)

FieldTypeRequiredDescription
project_id / cluster_locationstringYesGoogle Cloud project ID and region/zone of the GKE cluster (for example, "us-central1").
cluster_namestringYesName of the target GKE cluster.
namespacestringYesTarget Kubernetes namespace ("dev", "prod", or "default"). Created automatically if it does not exist.
artifact_registrystringYesArtifact Registry Docker repository URI used for container images deployed to the cluster.
manifest_pathstringYesLocal path to the Kubernetes manifest directory or file (for example, "./kubernetes-manifests/").
require_confirmationbooleanOptionalWhen true (enforced on prod), requires explicit user confirmation before applying manifests.

4. Developer Connect and Cloud Build settings (developer_connect_and_cloud_build)

FieldTypeRequiredDescription
build_modestringYesSet to "Developer Connect + Cloud Build" to enforce remote builds via Cloud Build triggers linked to your Git provider (GitHub, GitLab, or Bitbucket) instead of local Docker builds.
developer_connect.location / connection_idstringYesRegion and ID of the pre-configured Developer Connect connection for GitHub, GitLab, or Bitbucket.
cloud_build_trigger.project_id / regionstringYesGoogle Cloud project ID and region where the Cloud Build trigger runs.
cloud_build_trigger.service_accountstringYesFull resource name of the dedicated, user-managed Cloud Build service account (projects/<PROJECT_ID>/serviceAccounts/<SA_EMAIL>). Must not be the default Compute Engine service account.
cloud_build_trigger.default_branchstringYesBranch regex pattern for the Cloud Build trigger (for example, "^main$"). When running the trigger manually, the agent resolves the remote repository’s default branch and strips ^ and $.
cloud_build_trigger.auto_run_triggerbooleanOptionalWhen true, automatically executes gcloud builds triggers run after creating or updating the trigger.

Built-in security and operational guardrails

Remote CI/CD Execution (CLOUD_LOGGING_ONLY & --inline-config)

Links your GitHub, GitLab, or Bitbucket repository to Developer Connect and builds on Cloud Build using your dedicated service account with options: { logging: CLOUD_LOGGING_ONLY }. Automatically synthesizes an --inline-config payload if Dockerfile or cloudbuild.yaml is not yet committed to your remote default branch.

Pre-Build Secret Interception

Scans your workspace for .env files, private keys (*.pem, *.key), service account JSON keys, and hardcoded secrets in Dockerfile ENV/ARG instructions before building. Excludes sensitive files via .dockerignore and .gcloudignore and recommends Google Cloud Secret Manager (--set-secrets).

SPDX SBOM Generation & Binary Authorization (prod)

Exports an SPDX Software Bill of Materials (gcloud artifacts sbom export) for built images and enforces Binary Authorization (--binary-authorization=default) on prod Cloud Run deployments—verifying cryptographic attestations prior to rollout and diagnosing IMAGE_UNTRUSTED policy violations with exact remediation commands.

Automatic Agent Registry Registration

Detects AI Agents (google-adk, langchain, langgraph, crewai, autogen) and MCP Servers (mcp, fastmcp, @modelcontextprotocol/sdk) and automatically applies Google Cloud Agent Registry discovery labels on Cloud Run and GKE.
